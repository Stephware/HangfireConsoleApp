# StudentOperations — Activity Four setup

This repository implements the instructor's StudentOperations activity as four
.NET 10 projects inside the HangfireConsoleApp repository. It includes
SQL Server EF Core 10, Hangfire, an InitialCreate migration, and the
console menu/job types from Parts 1–10 of the handout.

The console application's classes and menu actions follow the handout.
Small adjustments were made so the app can use SQL Server from macOS:
the appsettings.json file is copied into the output folder, database settings
can be overridden with environment variables, and ConsoleMenu is scoped
as required by the correction in Part 7. The retry attribute from Part 10
is already on EnrollmentJob.ProcessAsync.

## 1. Build on your Mac

This project requires .NET 10 SDK. Run from the repository root:

    dotnet --version
    dotnet restore
    dotnet build

The solution is StudentOperations.slnx. The four projects are:
StudentOperations.Domain, StudentOperations.Application,
StudentOperations.Infrastructure, and StudentOperations.Console.

Install/update the EF Core CLI to the project's 10.0.12 version:

    dotnet tool update --global dotnet-ef --version 10.0.12

If not yet installed, use:

    dotnet tool install --global dotnet-ef --version 10.0.12

## 2. Launch SQL Server in Docker

The instructor's LocalDB connection works only on Windows. On macOS
a TCP connection to a SQL Server instance is required.

First identify your processor:

    uname -m

Intel Macs (`x86_64`) can try the included Docker Compose configuration.
Apple Silicon Macs (`arm64`) can also TRY it with x86-64 emulation, but
Microsoft does not test/support SQL Server container images on emulated ARM
hosts. Docker may fail or SQL Server may crash. If so, use a reachable
SQL Server hosted on Windows, Linux x86-64, or a cloud provider.

Docker Desktop must be running. From the repository root choose your own
strong SA password (do not put it in GitHub or a screenshot), then run:

    export MSSQL_SA_PASSWORD='ChooseYourOwnStrongPassword2026!'
    docker compose up -d
    docker compose ps
    docker compose logs --tail=60 sqlserver

Ensure Docker Desktop has enough memory allocated; SQL Server containers
may not start with very limited memory.

If the database refuses to start on Apple Silicon, the problem is an
unsupported SQL Server container architecture, not the console code.
Use a remote x86-64 SQL Server instead of rebuilding the .NET application.

## 3. Connect through DBeaver

For local Docker:
- Driver: Microsoft SQL Server
- Host: localhost (127.0.0.1)
- Port: 1433
- Database: master
- Authentication: SQL Server authentication
- Username: sa
- Password: the one from MSSQL_SA_PASSWORD
- Trust server certificate: enabled (for this local development setup)

Test the connection. Execute Database/CreateHangfireDatabase.sql in
DBeaver against the server. This creates an empty database named
StudentOperationsHangfireDb. Hangfire creates its tables inside that
database at runtime.

The StudentOperationsDb database will be generated by the EF migration.
SQL Server must be accepting connections before running migrations.

## 4. Point both .NET connections at Docker

From the same terminal session as your database run, execute these commands
(replace localhost, the username and password if using a remote server):

    export ConnectionStrings__StudentDatabase="Server=127.0.0.1,1433;Database=StudentOperationsDb;User Id=sa;Password=${MSSQL_SA_PASSWORD};Encrypt=True;TrustServerCertificate=True;"
    export ConnectionStrings__HangfireDatabase="Server=127.0.0.1,1433;Database=StudentOperationsHangfireDb;User Id=sa;Password=${MSSQL_SA_PASSWORD};Encrypt=True;TrustServerCertificate=True;"

Environment variables override the Windows LocalDB values in
StudentOperations.Console/appsettings.json. The EF design-time factory
reads ConnectionStrings__StudentDatabase too.

For a new terminal session, export these variables again.

## 5. Apply the included migration

The InitialCreate migration files and model snapshot are already included.
Do NOT create another InitialCreate migration.

    dotnet ef migrations list --project StudentOperations.Infrastructure --startup-project StudentOperations.Console
    dotnet ef database update --project StudentOperations.Infrastructure --startup-project StudentOperations.Console

In DBeaver refresh databases/tables. Verify StudentOperationsDb has:
Students, EnrollmentRequests, ProcessingLogs, and __EFMigrationsHistory.

## 6. Run the application

    dotnet run --project StudentOperations.Console

The menu provides options 1–7 plus Exit, matching Part 7.
The recurring job "process-pending-enrollments" is registered at startup
and scheduled every minute; it is not a menu selection.

A note on tests: every-minute recurring jobs may process a Pending request
before an immediate, delayed, continuation or batch demonstration runs.
Create the requests immediately before selecting the intended job action,
and verify job records as well as enrollment status.

## 7. Part 11 demonstration checklist

A. Register at least two students with option 1; use option 2 to create
   two enrollment requests; verify Students and initial Pending status.
B. Use option 3 for an immediate request; option 4 for a request delayed
   one minute; check eventual Completed status and timestamps.
C. Create a new Pending request without manual scheduling; wait for the
   one-minute recurring job and verify it completes.
D. Create a request; use option 5; verify completion followed by
   ConfirmationSent = true and a confirmation log.
E. Create several Pending requests; use option 6; verify batch processing
   and individual log entries.
F. Create a request with Simulate a temporary failure = y; select
   option 3; observe a failure followed by a retry and Completed.
G. Schedule a delayed request with option 4, exit before it executes,
   relaunch, and confirm the job persisted.
H. Restart the app several times; check HangFire's recurring job data
   for the same identifier "process-pending-enrollments".

Use Database/VerifyStudentOperations.sql to inspect student/enrollment/log
records after each test. Hangfire job metadata lives in
StudentOperationsHangfireDb (HangFire schema).
